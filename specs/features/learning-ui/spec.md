# Learning frontend

This is the frontend slice commissioned from the published `piano-learning` plan on `seeko/work`. It does not deliver the complete learner engine, authentication, inference, scheduling, or cloud persistence. Explicit task authorization selects this bounded work independently of automatic milestone picking.

## Plan
1. Port the accepted split-pane learning layout to Next.js routes.
2. Prepare one contextual next activity on the graph home, with a reason and direct Start/Resume entry; retain the four focused activities.
3. Compare the first working baseline with mlhacky.com and apply evidenced visual principles in a piano-specific identity.

## Requirements
- Keep the existing activity routes and legacy hubs available, but make `/learn` the agent-directed desktop home. Prepare one next activity with a short reason and one primary Start/Resume action. A learner can enter it directly without choosing Learn/Review, Theory/Procedure or a graph node. Learn/Review describe activity intent, not a required category-navigation step. The brand returns to this home.
- Route compatibility: `/learn` (overall home), `/learn/explore` (Learn hub) and `/learn/review` (Review hub). Keep activity URLs `/learn/understand`, `/learn/practice` and `/learn/play-through`; Review theory lives at `/learn/review/theory`. These hub routes are optional compatibility/exploration destinations, not the primary entry flow; duplicate category navigation must not compete with the prepared action.
- The overall home is an interactive demo mastery graph, with separate Theory and Procedure views. The graphs remain separate Theory and Procedure datasets/views; do not merge their nodes or relationships. Graph exploration is optional and does not select the prepared recommendation. The default exploration view is an unselected full-width overview with six unevenly placed broad hubs per domain, dense meaningful outward descendants, subtle deeper previews and selective labels, following the supplied screenshot and actual Spark subject-map source; grouping and prerequisite arrows are distinct. Subject definitions, sample learner states and sample goal inputs remain separate. The illustrative foundations slice is visibly labeled and never claims measured mastery or a universal validated curriculum. Every node, including broad parents, uses the same three projected mastery colors and shape patterns. Accessible names retain the projected level and fictional/prior source; no student-facing color legend, color explanation or review-due marker is shown. Selecting a skill shows context and a contextual action only when its sample foundations and available demo lesson support one. Unsupported skills never silently launch an unrelated Twinkle activity.
- Subject/world layout returns renderer-independent x/y/z positions with z=0 for the current 2D view. SVG projection, viewport fitting, pan/zoom/Fit and screen-space label placement are separate. Selecting or viewing never re-lays out the subject or changes learner state; no speculative 3D renderer is included. Root labels clear visible satellites, including preview nodes. Captions keep compact 18px/14px system-ui roles, restrained weights and tracking, with clean foreground paint over existing clearance boxes rather than a heavy text halo. The inspector appears only after selection and can close back to overview.
- The home guide presents the prepared activity independently of graph selection, domain tabs, pan and zoom. Browsing or dismissing graph details must not silently replace that activity or erase an unfinished session. A compact in-app gator companion may float in free overview space. Its primary action is Start for a fresh prepared activity or Resume for its actual unfinished local session; it opens the matching activity directly with skill and musical-example context. Use one short suggestion and a plain-language reason grounded in the available goal/state. The current domain-local fixture may supply candidate evidence, but changing the exploration domain must not act as a new recommendation decision. It subtly marks the actual target node without altering subject geometry or mastery. The prominent gator/Up next group stays top left and clear of graph roots/actions at both desktop sizes. Main Start/Resume moves the camera into that actual projected target over roughly800ms before routing once; reduced motion routes directly. Repeated clicks and unmount must not schedule duplicate or stale navigation. During prepared entry, existing captions retain their node-relative anchors; unrelated captions fade and threshold details do not appear mid-flight. Static collision placement remains unchanged. This frontend prototype may use an explicitly identified prepared demo fixture; no connected autonomous agent, validated recommendation policy, sound or automatic session start is implied. Accessible collapse persists across learning navigation. Selection and camera exploration may suppress the floating companion to protect inspected content, while preserving the prepared activity and a clear way back to it. Idle movement stops while hidden or when reduced motion is requested.
- An optional graph skill action explicitly enters only its supported contextual activity, preserving that skill and named example. Selecting, panning or viewing a node never starts a session or replaces the prepared recommendation. Unsupported skills remain inspectable without a launch.
- Entry belongs to the prepared home action or an explicit supported exploration action; a manual hub choice is not required. Optional hubs may retain direct activity entries. First entry shows Start; an unfinished local session shows Resume and restores its actual question, answers, material or practice settings. On completion, show the useful result and one primary return to the agent/map home. This increment retains the completed prepared example with an explicit Start again action; completion does not fabricate a new assignment, mastery, a due date or a model inference. An explicit secondary repeat action may reset a completed activity; Resume must never silently restart it. State belongs to the persistent learning layout and clears on refresh or leaving learning. No fabricated progress or backend is implied.
- Separate demo recommendation evidence from future real integration. The existing fixture goal is “Play short melodies with clear, steady endings”; phrase endings and short-phrase coordination are developing in the fictional overlay, have connected Twinkle activities and eligible sample prerequisites. `recommendation(domain)` selects the first eligible target in authored goal order, not a learned ranking. Due flags are authored examples, not a computed schedule. This can justify a modest goal-based demo reason, but cannot establish which activity is best for a real learner or whether Theory should precede Procedure. A real agent/learner-model handoff must eventually supply the prepared activity and evidence-based reason; that integration is outside this frontend increment.
- Each graph node has a retained mastery distribution, independently authored for parents rather than averaged from children. This prototype uses fictional distributions and disclosed uniform demo priors where no example evidence is authored; missing evidence is not measured failure. A coarse expected-level projection supplies three display buckets while preserving raw mass and source. Compatibility eligibility and authored review scheduling remain internal, separate from presentation. No fitted posterior, validated threshold, connected learner model or new inference engine is claimed.
- Reuse Eric's current shared font roles and tokens: Saira italic 900 headings/wordmark, italic 800 menu/actions/song titles, system-ui reading/control labels. Keep top navigation restrained. Dark score panels use off-white notation including SVG text/glyph fill; music glyph fonts and geometry remain unchanged. A playing phrase is emphasized only while existing audio state reports it playing.
- Theory uses a flat full-height question/reference split, initially 40/60, based on the current Spark encoding workspace. A persistent musical-task header sits above independently scrolling question/answer history, with the current answer and one primary Check/Continue action anchored below. The material pane scrolls independently; its selected source stays open while Learn questions progress. A pointer and keyboard accessible divider respects minimum pane widths. No fake chat or duplicate navigation.
- Learn theory permits the reference; Review theory unlocks it only after submitting the current answer. Closed answers get computed feedback; open explanations compare with a reference, never fabricated semantic grading.
- Learn practice fades support; Review practice retains the score and gives feedback after a performance. Preview takes and observations are visibly illustrative, with no invented mastery or saved account claims.
- Existing cited repository score data is reused, with provenance retained. Original teaching summaries distinguish melodic closure from harmonic cadence evidence.
- Leaving a session for the map or a hub stops active audio, count-ins and preview takes; Resume restores safe stopped state and retains the underlying answers/settings/results. Offline recovery names the connection problem and sync limits, preserves in-memory answers, history, practice settings and completed results, and cancels active audio, count-ins and preview takes. The anonymous arcade, game loop, root styles, frozen contracts and dependencies stay unchanged.

## Validation
- `pnpm -C web test`: question feedback, phrase selection and procedural state checks.
- `pnpm -C web lint`, `pnpm -C web typecheck`, `pnpm -C web build` pass.
- In visible Chrome, open each route at 1440x900 and 1280x800. Check the agent-directed home and optional compatibility hubs. Verify one prepared activity/reason/Start action, no required category choice, direct contextual entry, and question history, fixed answer/focus regions, independent material selection and scrolling, divider bounds and keyboard resizing. Verify loaded Saira faces and computed font roles, plus dark staff/notehead/clef/time-signature/text contrast without changing music geometry. Navigate all four activities; check a correct/incorrect answer, compare an explanation, use hints and audio, complete review, and confirm reference is locked before each review answer.
- On the graph at both desktop sizes, check Theory/Procedure tabs, arrow-key selection/focus, honest unsupported-skill context and all five available skill mappings to the correct contextual activity. Confirm graph browsing never changes the prepared recommendation or merges the separate datasets. Compare the actual Theory/Procedure screenshots at 1440x900 and 1280x800 directly with the supplied reference: full-width organic backbone, meaningful fans, deeper previews, six broad labels and no default inspector. Check label clearance against preview satellites, zoom/detail reveal, pan, Fit, close-to-overview and a selected group. Confirm inspector actions remain visible, the inspector scrolls independently, and a hard reload has no hydration warning. Tests establish behavior; visual fidelity requires the screenshot comparison.
- For the prepared recommendation and companion, inspect both domains at both desktop sizes plus selected/collapsed states. Confirm its target/reason/action agree with the fixed prepared fixture, collapse/reopen focus and persistence work, camera/selection do not replace the prepared activity, world geometry does not move, the asset loads, and reduced-motion/background states stop idle movement. Confirm all parents/leaves use their display projection, no legend/due marker appears, and top-left prominence clears roots/actions at both sizes. Record intermediate/final camera positions during actual Start/Resume, confirm the true target centers before one route, and verify reduced-motion direct entry plus duplicate-click/unmount guards. Compare static caption clarity at both sizes and record caption offsets/opacity during entry: target anchors must not jump between collision candidates, unrelated labels must fade, and direct entry/Resume/offline cancellation must still work.
- Follow Home -> prepared Start -> answer/progress -> Home -> Resume and verify the same activity, question, draft, history and selected reference. Switching graph domains or exploring another node must not reset this state. Enter both Review sessions through explicit contextual actions. Complete an activity and verify the result returns primarily to agent/map home, with no invented mastery update. Verify a completed Review can explicitly restart, and navigation during demo/count-in cancels playback without losing settings.
- Start a procedural preview take, fade support, play through, and verify feedback occurs after completion. Keep four desktop stills and laptop evidence outside the repository.
- With an owned background learning tab selected in visible Chrome, run `chrome-devtools-axi run < web/src/learn/frontend/offline.browser.mjs` to check offline recovery across all four activities, cancellation and fresh playback.
- Run repository ownership, gate and marker checks. The repository's game verification is separate from learning-route verification.
